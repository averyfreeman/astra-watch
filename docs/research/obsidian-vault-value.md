# Obsidian’s Value for Astra Watch Documentation

**Research checked:** 2026-10-02  
**Scope:** Project Memory Core, Obsidian’s built-in Markdown/vault features, and the documentation layout in the Astra Watch and Project Agent workspaces.

## Bottom line

An Obsidian vault adds more than a convenient file browser when a project has a growing, intentionally linked body of human-facing knowledge: backlinks expose which notes refer to a note, graph views visualize linked notes, and properties/Bases can turn curated metadata into reviewable indexes and dashboards. But putting Markdown in a vault does not itself improve its truth, make Codex load it, enforce ADR immutability, or create a code graph. Those benefits require explicit links, metadata, and a maintained human-facing entry point. If the vault is only a folder of otherwise unlinked notes, the material gain over a normal Markdown editor is small. ([Backlinks](https://obsidian.md/help/Plugins/Backlinks), [Graph view](https://obsidian.md/help/Plugins/Graph%2Bview), [Bases](https://obsidian.md/help/bases))

Project Memory Core is not solely a global Codex memory. Its published guide describes durable knowledge registered per project, including a project ID and a project folder inside the vault; a single vault may hold several repository registrations. The plugin manifest points to skills, and the skill guides Codex’s local file operations, reviewed promotion, retrieval, and health checks. Thus the *vault* is the portable file store and Obsidian interface; Project Memory Core contributes the curation and retrieval workflow. It is project-scoped memory, not an enforced project specification or an always-on global database. ([README](https://github.com/DuncanMain/project-memory-core#readme), [user guide](https://github.com/DuncanMain/project-memory-core/blob/main/docs/user-guide.md), [plugin manifest](https://github.com/DuncanMain/project-memory-core/blob/main/.codex-plugin/plugin.json), [curation skill](https://github.com/DuncanMain/project-memory-core/blob/main/skills/curate-project-memory/SKILL.md))

## What Obsidian changes—and what it does not

An Obsidian vault is an ordinary local folder of Markdown and other files. Obsidian refreshes its view when files change externally, so CLI and editor-created notes do not need conversion or a separate import step. Its internal links can use standard Markdown or Obsidian wikilinks; Graph view visualizes those note links. Properties add structured metadata to Markdown, and Bases uses that metadata to provide sortable/filterable database-like views while keeping note content in Markdown. These features can materially improve navigation and review once the project maintains useful links and fields; a graph is only a graph of recorded links, not a semantic map of the code. ([How Obsidian stores data](https://obsidian.md/help/Files%2Band%2Bfolders/How%2BObsidian%2Bstores%2Bdata), [internal links](https://obsidian.md/help/Linking%2Bnotes%2Band%2Bfiles/Internal%2Blinks), [Graph view](https://obsidian.md/help/Plugins/Graph%2Bview), [Properties](https://obsidian.md/help/Editing%2Band%2Bformatting/Properties), [Bases](https://obsidian.md/help/bases))

Obsidian is a presentation and navigation layer, not a policy boundary. It cannot ensure an agent follows a prompt, verify a claim against source, or prevent a user or another editor from modifying a file. Obsidian-specific block references and `.base` views also do not travel as ordinary Markdown behavior everywhere; prefer standard relative Markdown links for shared documentation and treat app-specific views as optional. ([Internal links](https://obsidian.md/help/Linking%2Bnotes%2Band%2Bfiles/Internal%2Blinks), [Bases syntax](https://obsidian.md/help/bases/syntax))

## Fit for these projects

| Documentation | Vault value | Recommended treatment |
|---|---|---|
| Human project home, research, glossary/domain terms, architecture maps, verification summaries | High when they link concepts, evidence, and decisions; a home note and local graph make those paths easier to browse. | Keep the Markdown canonical. Add a concise project home/index and links between related reports, concepts, and evidence. Use properties/Bases only if a real review question needs a dashboard. |
| ADRs and accepted decisions | Useful for finding, filtering, and following supersession; not for enforcing immutability. | Preserve each accepted ADR as its canonical immutable revision. Link it from a decision index; do not copy its prose into a second editable note or retrofit frontmatter into an already immutable record. Add metadata when creating future records only if it is part of the canonical write path. |
| `AGENTS.md`, `project_prompt.md`, skills, intake guidance, `project.config.toml`, and runtime records | Low as an Obsidian-specific layer. They may remain visible/searchable in the project folder, but vault status does not make them active Codex instructions or validated configuration. | Keep concise agent instructions and typed configuration in their existing canonical formats. Let Codex/Astra Watch load and validate them through their intended mechanisms, not through Obsidian. |

This matches Astra Watch’s stated architecture: accepted decision records are content-addressed and append-only in the tool’s write path, with Markdown ADR projections for human access; the report explicitly says those local controls are not signed or tamper-proof against a privileged user. Obsidian should therefore be a view of the canonical record, not a second authority. ([Astra Watch architecture decisions](../../ARCHITECTURE-DECISIONS.md#immutable-intent-mutable-execution))

There is already a useful local experiment. In this workspace, `project-agent/.obsidian/core-plugins.json` enables Graph, Backlinks, Properties, and Bases; `astra-watch` currently has no `.obsidian` directory. The predecessor’s reports and ADRs are ordinary Markdown with links, so the existing vault can demonstrate navigation without rewriting them. For Astra Watch, open its project root as a separate vault if that interface proves useful; avoid placing one vault inside another, which Obsidian cautions can break internal-link behavior. ([How Obsidian stores data](https://obsidian.md/help/Files%2Band%2Bfolders/How%2BObsidian%2Bstores%2Bdata))

## Low-friction workflow across ChatGPT and Codex CLI

Use each project folder as its canonical documentation home and Obsidian vault—no mirrored “Obsidian copy.” Keep those files under source control when the project uses Git. Put research outputs in one stable location such as `docs/research/`, keep reports in standard Markdown, and maintain a small index that links to them and to canonical ADRs. For the best shared-path workflow, attach that same local folder to a ChatGPT **local project** and make it primary; run Codex CLI from the folder or pass `codex -C <project-root>`. Open that root in Obsidian. Obsidian refreshes externally changed files, so either tool’s saved report appears there without a conversion step. ([OpenAI Projects and local projects](https://learn.chatgpt.com/docs/projects), [How Obsidian stores data](https://obsidian.md/help/Files%2Band%2Bfolders/How%2BObsidian%2Bstores%2Bdata))

Important boundary: an ordinary ChatGPT Project does not directly access a folder on the computer. If a task is not using a local project (or its attached folder), save/download its Markdown artifact into the project’s `docs/research/` directory and review the resulting diff and links. Do not assume conversation sync or Obsidian Sync will merge separate task workspaces automatically. OpenAI distinguishes local project folder access from ChatGPT Projects; Codex CLI uses its working directory independently. ([OpenAI Projects and local projects](https://learn.chatgpt.com/docs/projects))

**Recommendation:** adopt Obsidian as an optional, per-project human knowledge interface—not as a new documentation format or enforcement layer. Start with a project home and links among research, concepts, decisions, and evidence. Add metadata dashboards only when they answer a recurring question. Keep agent scaffolding, runtime state, and immutable ADR authority in Astra Watch’s existing mechanisms. The predecessor already has the vault configuration; the successor can be opened as its own vault without changing plugin behavior.
